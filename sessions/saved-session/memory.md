Hostinger's deployment runner doesn't do that.  \n**Rule:** On Hostinger, use default Next.js output (no `output` key). Use root `server.js` with `createServer + getRequestHandler` pointing `dir` to `frontend/`. Never add `standalone` unless you control the execution environment.\n\n### L-003 \u2014 Deployment verification must be a mandatory step, not optional\n**What went wrong:** After pushing, we assumed auto-deploy would work. No one checked. The site was broken for real users while we considered the work \"done.\"  \n**Root cause:** No enforced post-deploy checklist existed.  \n**Rule:** The session is not complete until the live site is verified. Add to every session checkpoint: \"Verified on investogram.org: YES / NO / BLOCKED.\"\n\n---\n\n## 2. Environment Variables\n\n### L-004 \u2014 `.env.local` committed to git \u2192 wrong URL baked into production build\n**What went wrong:** `frontend/.env.local` had `NEXT_PUBLIC_API_URL=http://127.0.0.1:8000`. Next.js `.env.local` overrides `.env.production` at build time.  \n**Rule:**\n- `.env.local` = local dev only \u2192 always in `.gitignore`, never committed\n- `.env.production` = production config \u2192 committed, contains Render backend URL\n- After deploy, verify by running `window.NEXT_PUBLIC_API_URL` in browser console on live site\n\n### L-005 \u2014 `NEXT_PUBLIC_*` variables are build-time, not runtime\n**What went wrong:** We changed the env var on Hostinger's dashboard and expected it to take effect immediately. Runtime env vars are for server-side code only.\n\n---\n\n## 3. CORS & Network\n\n### L-006 \u2014 Production domain never hardcoded in CORS \u2192 all API calls blocked\n**What went wrong:** CORS allowed `investogram.org` only if `FRONTEND_URL` env var was set on Render. That var was absent. Every API call from the live site returned a CORS error, invisible to backend logs.  \n**Root cause:** CORS was made conditional on an environment variable that could be missing.  \n**Rule:** Production domains must be **hardcoded** in `app/api.py` CORS origins. Never make them conditional. `investogram.org` and `www.investogram.org` are permanent entries regardless of env.\n\n### L-007 \u2014 CORS errors are browser-only; they are invisible in backend logs\n**What went wrong:** We checked Render logs and saw no errors. Assumed API was working. CORS errors only appear in the browser DevTools Console \u2014 the backend never sees them.  \n**Root cause:** Misunderstanding of where CORS enforcement happens (browser, not server).  \n**Rule:** When an API call fails silently, the first debug step is always **browser DevTools \u2192 Console tab \u2192 look for CORS errors**. Backend logs cannot detect CORS failures.\n\n---\n\n## 4. Authentication & Security\n\n### L-008 \u2014 Using `alert()` for auth errors \u2192 silent failures on mobile\n**What went wrong:** Login/signup errors used `alert(error.message)`. On mobile browsers and some desktop settings, `alert()` can be blocked or dismissed before the user reads it. Users saw nothing, couldn't understand why auth failed.  \n**Root cause:** `alert()` is a dev shortcut, not a production UX pattern.  \n**Rule:** All errors in production must render **inline in the UI** as visible, persistent elements. Never use `alert()`, `confirm()`, or `console.error()` as the primary error surface for users.\n\n### L-009 \u2014 Supabase callback URL not registered \u2192 auth breaks after deploy\n**What went wrong:** After deploying to Hostinger, Supabase auth redirected to a URL (`https://investogram.org/auth/callback`) that wasn't registered in the Supabase dashboard. Auth silently failed.  \n**Root cause:** Supabase's OAuth security model rejects redirects to unregistered URLs. Local dev had `localhost:3000` registered but not the production URL.  \n**Rule:** Every new domain deployed to must have its `/auth/callback` URL added to Supabase \u2192 Authentication \u2192 URL Configuration immediately. Add this to the deployment checklist.\n\n### L-010 \u2014 Old Supabase cookie API breaks SSR sessions\n**What went wrong:** `proxy.ts` used the old `.get/.set` single-cookie pattern. Modern `@supabase/ssr` requires `getAll/setAll` for multi-cookie session management. SSR sessions silently failed.  \n**Root cause:** Package upgraded, cookie API changed, code wasn't updated.  \n**Rule:** When upgrading `@supabase/ssr`, always check the cookie API migration guide. Use `getAll/setAll`. Do not revert to the old pattern.\n\n### L-011 \u2014 IDOR risk: backend didn't enforce user-level filters\n**What went wrong:** `/api/screen` applied competence and firewall filters only if the frontend sent them. Backend trusted frontend inputs. A malicious user could strip filters and see all stocks.  \n**Root cause:** Security filters were frontend-enforced, not backend-enforced.  \n**Rule:** Security decisions (what data a user can see, what actions they can take) are always enforced on the backend. Frontend UI is just presentation \u2014 never trust it for access control.\n\n### L-012 \u2014 DEV_MODE env variable bypassed all authentication\n**What went wrong:** `DEV_MODE=true` returned a mock user profile for all requests, skipping auth entirely. If deployed with this flag on Render, any user could access any endpoint unauthenticated.  \n**Root cause:** Dev convenience flag exposed in production configuration.  \n**Rule:** `DEV_MODE` must be gated to local environments only.
